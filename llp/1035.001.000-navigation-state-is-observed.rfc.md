# LLP 1035.001.000: Native navigation is a projection, and what it shows is observed

**Type:** RFC
**Status:** Draft
**Systems:** iOS host (`NavigationIOS.swift`, `ModalIOS.swift`, `TabContainersIOS.swift`, `MenusIOS.swift`, `NavigationRules.swift`), Agent API (`state.navigation`)
**Author:** Claude (Opus 5.5) for ide
**Date:** 2026-10-04
**Related:** LLP 1035.001 D1 (the route vocabulary, the Back control), D2 (three outcomes, one dispatch), D4 (the presenting owner), D6 (refusals are journal lines); LLP 1038 D6 (push-or-swap; the 2026-09-26/27 amendments), D7 (the web's history mirror, which already works this way), D12 (tabs); LLP 1008 §9; LLP 1035.002 D2 (`state.navigation`); commits `52687f4d`, `7d8e03dd`

## Summary

The app's router value is the only navigation state. The iOS host
projects it into UIKit — a tab bar controller, one navigation controller
per tab, a presented navigation controller per sheet — and UIKit sometimes
changes what it shows on its own: the back button, its long-press menu,
the edge swipe, iOS 26's content swipe, a sheet pulled down, VoiceOver's
escape, a keyboard shortcut, and whatever comes next.

Today each of those is a separate path that reasons about *how* it
happened (an interactive source captured at `willShow`, a depth at the
swipe's start, a sheet's own dismissal delegate). This RFC replaces them
with one reconciler and two directions:

- **App → native.** When the app's tree changes, project it — unless a
  native transition is in flight; then wait, and project the latest tree
  when it settles. Record what was projected (**applied**).
- **Native → app.** When any native container settles, read what UIKit
  now shows (**observed**) and compare it with **applied**. The host
  changed nothing in between, so any difference is the platform's. It is
  always "the person went back to screen K" (or, for a tab, "selected T"),
  and it is delivered through the app's own controls before anything is
  projected again.

How UIKit got there never matters. A gesture added in iOS 28 is covered
the day it ships.

### Bugs, with repros

B1 was reproduced on a simulator with real UIKit chrome; B2–B6 are from
reading the code and have not been reproduced (each names how to).

**B1 — A multi-screen pop reports one screen, and the screen bounces back.**
`didShow` resolves the Back control once and presses that id `pops` times
(NavigationIOS 699–700). The control lives in the top route (it must: D1
resolves it in the active route), so the first press's batch destroys it;
the remaining presses go to a dead id. Worse, the first press's batch runs
`sync` re-entrantly inside `didShow` (`changing` is already false), which
projects the app's intermediate stack — one screen deeper than UIKit's —
and *pushes it back*, animated.
Reproduced 2026-10-04 on an iPhone 17 Pro simulator (iOS 27), Lexy
launched normally, with a test-only trailing button on Updates that pushes
Data State (the stock app is two deep): Settings → Updates → Data State;
hold the back button (`axe touch --down`), release on "Settings" in the
menu (`axe touch --up` at the item). UIKit pops to Settings and settles;
then Updates slides back in, animated, and stays. A recording's frames
show both steps.

**B2 — The app's newest change can be reported away as a platform pop.**
`poppedByPlatform(native:app:)` compares UIKit with the app's *current*
tree. While a transition is in flight `sync` defers (389), so the tree can
move ahead of UIKit; at `didShow` "native is a prefix of the app" then
means "the host has not applied the app's push yet", not "the platform
popped". Example: the app pops `b` (animated) and, before the animation
ends, pushes `c` (a link, a notification's `navigate`, a timer). At
`didShow` native is `[a]`, the app `[a, c]`, and the host presses Back:
`c` is gone. The same holds for a pop that coincides with a sheet in
transition (694: the pop is dropped instead).

**B3 — Selecting a tab during a push can leave `changing` set for good.** `installTabs`
switches `primaryNavigation` to the new tab's controller before the
in-flight guard. The old controller's `didShow` is then ignored
(`navigationController === navigation` fails, 661), so `changing` stays
true forever: every later `sync` only sets `pendingSync` (389), pushes and
sheets never appear, and `popMayBegin` refuses the swipe. Only a UIKit
back-button pop on the current tab (which re-runs `willShow`/`didShow`)
recovers. *Not reproduced:* a row tap followed by a tab tap 0.05–0.4 s
later (one `axe batch`) left navigation working, apparently because
setting `selectedIndex` (279) completes the outgoing transition, and its
`didShow` lands, before `primaryNavigation` moves (280). The hazard is
real; that the order happens to save it is not a design.

**B4 — The back button ignores the app's permission.** D1 says an app
blocks leaving by disabling its Back control; the swipe and sheet honour
that (`popMayBegin`, `isModalInPresentation`), but the bar's back button
and its menu are never hidden. A pop with no enabled control is silently
dropped (`guard … let control = backControl else { return }`, 699): UIKit
shows the parent, the app still shows the child, and the next unrelated
batch pushes the child back in. Any route with a title and a disabled (or
missing) Back control reproduces it.

**B5 — A sheet's dismissal is a separate, narrower path.** It requires
the sheet's root to be the selected key (`invokeBack`, 571–576), so a
sheet that has pushed a screen refuses the pull-down entirely
(`refusesDismissal` → `isInactiveRoute`), unlike every UIKit sheet; and if
the app changes the selection during the drag the dismissal is dropped
and the next `sync` re-presents the sheet. Two delegates
(`presentationControllerDidDismiss`, the zoom's `interactiveDismissShouldBegin`)
each have to be right, and a future dismissal path (iOS adds one most
years) would be a third.

**B6 — A refused presentation is never retried.** When the owner already
presents an alert, popover or share sheet, `canPresent` journals and
returns without setting `pendingSync`; nothing re-syncs when the alert
goes. The app shows the sheet's route as selected (its underlying routes
inactive for focus), UIKit shows no sheet, until some later batch.

### Where the code reasons about how, not what

- `interactiveSource`, `interactiveDepth`, `interactiveTransition`,
  `replacedBack`, `sourceReplaced`, `NavigationRules.dispatchesBack`
  (NavigationIOS 103–105, 545–546, 647–657, 674–697): capture a swipe's
  source to decide whether its completion may dispatch, plus an exception
  for a source replaced mid-swipe. Under §2 both cases fall out of
  *applied vs observed* with no special case.
- `lastTransition = "completed" | "cancelled"` (697): derived from the
  gesture, not from a state difference.
- `ModalHost.presentationControllerDidDismiss` → `invokeBack` (ModalIOS
  352–367): a per-mechanism report path.
- `pops = presenter.modals.inTransition ? 0 : …` (694): a report dropped
  for timing, not for meaning.

## 2. The model

### D1 — The app's value is the state; the host holds a projection record and nothing else

The host keeps, per session, exactly:

- **applied**: the `NavSnapshot` it last set on UIKit (below);
- **owed**: a platform change observed and not yet delivered (at most one);
- **dirty**: the app's tree changed while projection had to wait.

No interactive source, no depth at a gesture's start, no "completed".
In-flight is read from UIKit (`transitionCoordinator`,
`isBeingPresented`/`isBeingDismissed`, the modal host's retiring layers),
never a flag a missed callback can leave set (B3).

### D2 — One observation: a normalized snapshot

```swift
struct NavSnapshot: Equatable {
    var tab: String?            // the selected tab, nil untabbed
    var stack: [String]         // the selected tab's stack, by navigationKey, root first
    var presented: [[String]]   // each presented layer's stack, lowest first
    var chain: [String] { stack + presented.flatMap { $0 } }
}
```

Built from UIKit alone: `tabs.selectedIndex` → tab name; each owned
navigation controller's `viewControllers` → `RouteController.key`; each
`ModalController` still presented (not being dismissed) → its
navigation's keys. Alerts, action sheets, popovers, menus, context
previews and the share sheet are not `RouteController`s and are not in it:
they are not navigation. Detents, scroll, the bar's collapse, size class:
not in it. A non-stack tab container (`screen`, a module's) contributes
its root.

The app side is the same shape, computed from the tree as `projection()`
already does: `NavigationRules.segments` splits the selected chain into
`stack` and `presented`.

### D3 — Native → app: at every settle, diff observed with applied

**Settle points** all call one `settle()`, on the next main-queue turn
(outside UIKit's callback stack, after its coordinator is gone):
`navigationController(_:didShow:)` for any owned stack;
`ModalController.viewDidAppear`/`viewDidDisappear`; the modal host's
dismissal completions; a menu, alert, popover or share sheet's
dismissal; mount and reparent. `settle()` ignores its caller's arguments
and reads UIKit. If anything is in flight it returns (the transition's
own completion will settle again).

The rule, pure (`NavigationRules.platformChange(applied:observed:)`):

| observed vs applied | meaning | owed |
|---|---|---|
| equal | nothing happened, or a cancelled gesture | none |
| `tab` differs | UIKit selected a tab (More, customization; never today) | `select(tab)` |
| `observed.chain` a strict prefix of `applied.chain` | the platform took screens off the top: a pop of any depth, a dismissed sheet (with any stack inside it), nested sheets dismissed together | `backTo(observed.chain.last)` |
| anything else | UIKit holds something the host never set | none; journal once; re-project |

Then `applied = observed`. A second settle over the same UIKit state finds
them equal: a change is owed once, never twice.

The intent is a *key*, not a count. "Back to K" stays right when the app
moved during the gesture: B2's app push above `b` is not counted as
popped, because applied (what UIKit was showing) never held it; 1038 D6's
"source replaced while the finger was down" is the same rule (applied
held the old source; the app's top is its replacement; going back to K
removes it) with no exception.

### D4 — Delivery: the app's Back control, once per screen, re-resolved each time

`backTo(K)` is delivered before anything is projected (`sync` delivers
owed first; `settle` delivers at once):

```
while app.chain.last != K, app.chain.contains(K):
    control = backControl          // D1 of 1035.001: resolved now, in the now-active route
    guard control else { journal "back to K refused: no enabled Back control"; break }
    press(control)                 // commits synchronously
    guard app.chain changed else { journal "… refused by the app"; break }
```

Projection is suspended for the loop (`delivering`): the intermediate
trees are not pushed (B1's bounce), and one projection follows. If `K` is
no longer in the app's chain the app has gone elsewhere; nothing is
pressed and its state wins. If the app refuses a step, the projection
that follows puts the screens back: refusal is visible and deterministic
(1035.001 D2's "revocation re-presents", generalized).

Each step is the app's own Back for the screen being left — Lexy's login
preview resets its scenario, Last Parked runs `close` — exactly what one
tap on each would do. No Contract change is needed. `select(T)` presses
the tab's `navigationTabControl`.

### D5 — App → native: project the latest tree when nothing is in flight

`sync` = deliver owed; if in flight, set dirty and return; else project
the whole snapshot (tabs, the selected stack, presentations) and set
`applied` to what UIKit *reports* right after the calls (UIKit updates
`viewControllers` synchronously, animated or not). If that differs from
the target (UIKit refused a call) journal it and keep what UIKit reports:
the next settle cannot mistake the host's own failure for the person's.
A presentation that cannot start (another controller is presented: an
alert, the share sheet) leaves dirty set; that controller's dismissal is
a settle point, so it is retried (B6).

Animation is unchanged (1038 D6: push/pop when one list is a prefix of
the other, a cut otherwise).

### D6 — Permission is projected, not enforced after the fact

Whether leaving is allowed is app state (an enabled Back control in the
active route, `closedby`), projected declaratively where UIKit offers a
switch: the swipe recognizers' `shouldBegin` (today), a sheet's
`isModalInPresentation` (today), and `navigationItem.hidesBackButton` on
the top route (new: hides the button and its menu, B4). A platform path
nobody can switch off still ends in D3/D4: the app is asked, refuses, and
the screen comes back. The permission rule moves into
`NavigationRules.backPermitted(...)`, used by all three.

### D7 — Controls are not state changes

UIKit chrome that acts as a button changes nothing native and presses the
app's control: tab bar items (`shouldSelect` → false), trailing bar
buttons, the sheet backdrop with `closedby="any"`. The app's answer
arrives as an ordinary batch through D5. This is the existing behaviour,
named.

### D8 — Containers

- **Stack:** pops of any depth by any mechanism → D3 prefix rule.
- **Sheet (`modal`)**, with any detents: a dismissal is the loss of its
  layer → `backTo` the route beneath its boundary, however deep its own
  stack. Pull-down is permitted when Back is permitted on the sheet's top
  route and no route in the layer says `closedby="none"`. Detents are not
  state.
- **Full screen (`fullscreen`)**, including the iOS 18 zoom: the same.
- **Nested presentations:** dismissing a lower one dismisses all above;
  the chain shrinks to its boundary; one `backTo`.
- **Alerts, action sheets, popovers, menus, share:** not navigation; they
  only defer presentation (D5) and settle when they go.
- **Tabs:** selected only by the app (D7). The More tab: either support
  it (it is a stack UIKit owns; selecting a tab through it settles as
  `select(T)`) or refuse more than five tabs on iPhone with one journal
  line. Recommended: refuse until an app needs six.

### D9 — `state.navigation` reports the three values

`native` (observed), `applied`, `app` (the tree's snapshot), `owed`, and
`transition.phase` (`in-progress` while anything is in flight, else
`idle`). `completed`/`cancelled` go; the agent asserts on state.

## 3. What this removes

`interactiveSource`, `interactiveDepth`, `interactiveTransition`,
`lastTransition`, `changing`, `pendingSync`, `replacedBack`,
`NavigationRules.dispatchesBack`, `poppedByPlatform`,
`ModalHost.presentationControllerDidDismiss`'s `invokeBack`, and
`invokeBack`'s key check. `popMayBegin` keeps its permission half; its
`changing` argument becomes "in flight".

## 4. Verification

1. **Pure (`NavigationRulesTests`, macOS, no UIKit):** `platformChange`
   over a table — back button (1), back menu (3), cancelled swipe (equal),
   swipe whose source the app replaced (back to K), app push during a pop
   (back to K, not two), sheet pulled down with a pushed screen inside,
   nested sheets, a non-prefix (none), a tab change; idempotence (settle
   twice, owe once). The delivery loop against a fake app: refusal stops,
   `K` gone presses nothing, projection runs once.
2. **UIKit (`build.mjs --test --ios`, a real window):** the reconciler
   cannot tell a gesture from an API call, so the platform's changes are
   made by calling UIKit as its chrome does —
   `popToViewController(animated:)` (the back menu),
   `popViewController`, `dismiss` on the sheet — and the test asserts the
   app's presses and the final `applied`. Plus B3: `selectedIndex`
   changed during an animated push, then a push must appear.
3. **Simulator, real chrome (`axe` on a normally launched app, never the
   agent driver, which presses the hidden controls):** back button,
   long-press back → menu item, edge swipe completed and cancelled
   (`axe touch --down/--up` with moves), sheet drag to a detent and
   dismissed, tab tap during a push, alert over a sheet then a new sheet.
   Each step asserts on `state.navigation` (`native == app`, nothing
   owed). Adding a script for this is new apparatus and needs a human's
   yes (CLAUDE.md); until then it is a checklist.

## 5. Landing order

1. `NavSnapshot`, `platformChange`, `backPermitted` and their tests
   (pure; no behaviour change).
2. Observation + `applied` + `settle()` in `NavigationHost`; delivery
   with suspended projection; `sync` reads in-flight from UIKit. Removes
   the interactive bookkeeping. Fixes B1, B2, B3.
3. Sheets through `settle()`; their delegate keeps only permission. Fixes
   B5; dismissal with a pushed stack allowed.
4. `hidesBackButton` from `backPermitted` (B4); blockers as settle points
   (B6).
5. `state.navigation` fields; the simulator checklist on Lexy and
   Messages.

## 6. Open questions

1. **One richer intent instead of N Backs?** A router verb `backTo(r,
   id)` and a root event carrying the entry key would make a multi-pop
   one commit. It is cleaner for the router but skips each screen's own
   Back handler (Lexy's login preview relies on its own), adds a seventh
   verb to 1038's six, and the web's multi-step Back already uses
   `navigate(url)` instead (1038 D7). This RFC keeps N Backs; the question
   is whether 1038 should gain `backTo` for both hosts.
2. **The More tab:** support or refuse (D8)?
3. **Module containers** (`navigationContainer` = a module's): may user
   space change its own screens? If so, `NativeContainer` must report
   them for D2; today it is projection-only.

## 7. What this amends, at acceptance

LLP 1035.001 D2: "completion presses Back once" becomes "a settled native
state with screens off the top is delivered as Back to the shown route,
once per screen, each re-resolved"; the interactive-source repair and its
1038 D6 2026-09-27 exception are subsumed. LLP 1035.002 D2's
`state.navigation` gains D9's fields.
