# LLP 1035.001.000: Native navigation is a projection, and what it shows is observed

**Type:** RFC
**Status:** Draft r2 — implemented on `agent/nav-model` (exact2) for iOS and the web, with Lexy adopting it. r1 (2026-10-04) was the audit and proposal; the author's rulings the same day (a multi-screen Back is one event and a router verb, not N presses; support the More tab and its Edit as UIKit does; choose the container rule; axe-driven simulator tests) are folded in as D4, D8 and §4.

**Author:** Claude (Opus 5.5) for ide
**Date:** 2026-10-04
**Related:** LLP 1035.001 D1 (the route vocabulary, the Back control), D2 (three outcomes, one dispatch), D4 (the presenting owner), D6 (refusals are journal lines); LLP 1038 §3 (the verbs), D6 (push-or-swap; the 2026-09-26/27 amendments), D7 (the web's history mirror, which already worked this way), D8 (`navigate`), D12 (tabs); LLP 1008 §9; LLP 1035.002 D2 (`state.navigation`); commits `52687f4d`, `7d8e03dd`

## Summary

The app's router value is the only navigation state. The iOS host
projects it into UIKit — a tab bar controller, one navigation controller
per tab, a presented navigation controller per sheet — and UIKit sometimes
changes what it shows on its own: the back button, its long-press menu,
the edge swipe, iOS 26's content swipe, a sheet pulled down, VoiceOver's
escape, a keyboard shortcut, the More list, and whatever comes next.

Before this, each of those was a separate path that reasoned about *how*
it happened (an interactive source captured at `willShow`, a depth at the
swipe's start, a sheet's own dismissal delegate). Now there is one
reconciler with two directions:

- **App → native.** When the app's tree changes, project it — unless a
  native transition is in flight, or a platform change has not yet been
  told; then wait, and project the latest tree when it settles. Record
  what UIKit then shows (**applied**).
- **Native → app.** When any native container settles, read what UIKit
  now shows (**observed**) and compare it with **applied**. The host
  changed nothing in between, so any difference is the platform's. It is
  always "the person went back to the route keyed K" (or "UIKit selected
  tab T"), and it reaches the app — as one `traverse` event carrying K,
  where the root declares it — before anything is projected again.

How UIKit got there never matters. A gesture added in iOS 28 is covered
the day it ships. The web's history mirror (1038 D7) was already this
shape — what it wrote against the entry `popstate` lands on — and now
speaks the same event.

### Bugs, with repros

B1 was reproduced on a simulator with real UIKit chrome; B2–B6 are from
reading the code and have not been reproduced (each names how to).

**B1 — A multi-screen pop reports one screen, and the screen bounces back.**
`didShow` resolves the Back control once and presses that id `pops` times
(NavigationIOS 699–700). The control lives in the top route (it must: D1
resolves it in the active route), so the first press's batch destroys it;
the remaining presses go to a dead id. Worse, the first press's batch runs
`sync` re-entrantly inside `didShow` (`changing` is already false), which
projects the app's intermediate stack — one screen deeper than UIKit's —
and *pushes it back*, animated.
Reproduced 2026-10-04 on an iPhone 17 Pro simulator (iOS 27), Lexy
launched normally, with a test-only trailing button on Updates that pushes
Data State (the stock app is two deep): Settings → Updates → Data State;
hold the back button (`axe touch --down`), release on "Settings" in the
menu (`axe touch --up` at the item). UIKit pops to Settings and settles;
then Updates slides back in, animated, and stays. A recording's frames
show both steps.

**B2 — The app's newest change can be reported away as a platform pop.**
`poppedByPlatform(native:app:)` compares UIKit with the app's *current*
tree. While a transition is in flight `sync` defers (389), so the tree can
move ahead of UIKit; at `didShow` "native is a prefix of the app" then
means "the host has not applied the app's push yet", not "the platform
popped". Example: the app pops `b` (animated) and, before the animation
ends, pushes `c` (a link, a notification's `navigate`, a timer). At
`didShow` native is `[a]`, the app `[a, c]`, and the host presses Back:
`c` is gone. The same holds for a pop that coincides with a sheet in
transition (694: the pop is dropped instead).

**B3 — Selecting a tab during a push can leave `changing` set for good.** `installTabs`
switches `primaryNavigation` to the new tab's controller before the
in-flight guard. The old controller's `didShow` is then ignored
(`navigationController === navigation` fails, 661), so `changing` stays
true forever: every later `sync` only sets `pendingSync` (389), pushes and
sheets never appear, and `popMayBegin` refuses the swipe. Only a UIKit
back-button pop on the current tab (which re-runs `willShow`/`didShow`)
recovers. *Not reproduced:* a row tap followed by a tab tap 0.05–0.4 s
later (one `axe batch`) left navigation working, apparently because
setting `selectedIndex` (279) completes the outgoing transition, and its
`didShow` lands, before `primaryNavigation` moves (280). The hazard is
real; that the order happens to save it is not a design.

**B4 — The back button ignores the app's permission.** D1 says an app
blocks leaving by disabling its Back control; the swipe and sheet honour
that (`popMayBegin`, `isModalInPresentation`), but the bar's back button
and its menu are never hidden. A pop with no enabled control is silently
dropped (`guard … let control = backControl else { return }`, 699): UIKit
shows the parent, the app still shows the child, and the next unrelated
batch pushes the child back in. Any route with a title and a disabled (or
missing) Back control reproduces it.

**B5 — A sheet's dismissal is a separate, narrower path.** It requires
the sheet's root to be the selected key (`invokeBack`, 571–576), so a
sheet that has pushed a screen refuses the pull-down entirely
(`refusesDismissal` → `isInactiveRoute`), unlike every UIKit sheet; and if
the app changes the selection during the drag the dismissal is dropped
and the next `sync` re-presents the sheet. Two delegates
(`presentationControllerDidDismiss`, the zoom's `interactiveDismissShouldBegin`)
each have to be right, and a future dismissal path (iOS adds one most
years) would be a third.

**B6 — A refused presentation is never retried.** When the owner already
presents an alert, popover or share sheet, `canPresent` journals and
returns without setting `pendingSync`; nothing re-syncs when the alert
goes. The app shows the sheet's route as selected (its underlying routes
inactive for focus), UIKit shows no sheet, until some later batch.

### Where the code reasons about how, not what

- `interactiveSource`, `interactiveDepth`, `interactiveTransition`,
  `replacedBack`, `sourceReplaced`, `NavigationRules.dispatchesBack`
  (NavigationIOS 103–105, 545–546, 647–657, 674–697): capture a swipe's
  source to decide whether its completion may dispatch, plus an exception
  for a source replaced mid-swipe. Under §2 both cases fall out of
  *applied vs observed* with no special case.
- `lastTransition = "completed" | "cancelled"` (697): derived from the
  gesture, not from a state difference.
- `ModalHost.presentationControllerDidDismiss` → `invokeBack` (ModalIOS
  352–367): a per-mechanism report path.
- `pops = presenter.modals.inTransition ? 0 : …` (694): a report dropped
  for timing, not for meaning.

## 2. The model

### D1 — The app's value is the state; the host holds a projection record and nothing else

The host keeps, per session, exactly:

- **applied**: the snapshot UIKit showed when the host last projected;
- **owed**: a platform change observed and not yet delivered (at most one);
- **dirty**: the app's tree changed while projection had to wait.

No interactive source, no depth at a gesture's start, no "completed".
In flight is read from UIKit — any owned stack's, the tab bar
controller's or the More list's `transitionCoordinator`, a presentation
being presented or dismissed (`ModalHost.inTransition`) — never a flag a
callback that did not come can leave set (B3).

### D2 — One observation: a normalized snapshot

```swift
struct Snapshot: Equatable {            // NavigationRules.Snapshot
    var tab: String?                    // the selected tab, nil untabbed
    var stack: [String]                 // its stack, by navigationKey, root first
    var presented: [[String]]           // each presented layer's stack, lowest first
    var chain: [String] { stack + presented.flatMap { $0 } }
}
```

Built from UIKit alone (`NavigationHost.observe`): the tab UIKit shows,
including one shown inside the More list; that tab's stack — its
navigation controller's, or the More list's navigation controller's past
the list when UIKit has handed the stack to it, or what a non-stack
container shows; each presented navigation controller's keys. Alerts,
action sheets, popovers, menus, context previews and the share sheet are
not route controllers and are not in it: they are not navigation. Nor
are detents, scroll, the bar's collapse, size class, or the tabs' order.
The More list itself, open over the tab the app selects, is UIKit's
chrome, as a menu is: the snapshot keeps the tab and stack it had.

The app side is the same shape from the tree (`appSnapshot`):
`NavigationRules.segments` splits the selected chain into `stack` and
`presented`.

### D3 — Native → app: at every settle, diff observed with applied

**Settle points** all call one `settle()`, which runs on the next
main-queue turn (outside UIKit's callback, its coordinator gone):
`navigationController(_:didShow:)` for any owned stack or the More
list's; the end of any transition seen at `willShow` (its coordinator's
completion, which also covers a cancelled swipe); a presentation's
presentation and dismissal completions and its platform dismissal;
`tabBarController(_:didSelect:)` and `didEndCustomizing`; an alert,
popover or share sheet leaving. `settle()` ignores its caller and reads
UIKit; if anything is in flight it waits for that transition's
completion.

The rule, pure (`NavigationRules.platformChange(applied:observed:)`):

| observed vs applied | meaning | owed |
|---|---|---|
| equal | nothing happened, or a cancelled gesture | none |
| `tab` differs | UIKit selected a tab (in the More list) | `select(tab)` |
| `observed.chain` a strict prefix of `applied.chain` | the platform took screens off the top: a pop of any depth, a dismissed sheet with any stack inside it, nested sheets dismissed together | `backTo(observed.chain.last)` |
| anything else | UIKit holds something the host never set | none; the projection that follows restores the app's |

Then `applied = observed`; a second settle over the same UIKit state finds
them equal, so a change is owed once.

The change is a *destination*, not a count, so it stays right when the
app moved during the gesture: B2's push is never counted as popped,
because applied (what UIKit showed) never held it; 1038 D6's "source
replaced while the finger was down" is the same rule (applied held the
old source; going back to K removes its replacement) with no exception.

**One transition, one change.** The back button's long-press menu is
UIKit's `popToViewController`: one `willShow`, one `didShow`, one
animation from the top to the destination; the screens between leave the
stack without being shown. Observed on the simulator (iOS 27): from
Settings → Updates → Data State, choosing "Settings" in the menu logged
one `willShow 2 animated=true interactive=false` and one `didShow 2`, then
one settle (`applied` three deep, `observed` one) and one delivery,
`backTo("2")`. The platform treats it as one step; so does the app.

### D4 — Delivery: one `traverse` with the destination, or the Back control per screen

Contract gains one handler and one verb (LLP 1038 §3 amended):

- **`traverse`**, on the navigation root only (as `navigate`, `lower-navigate-root`):
  the platform took the person back to the route whose `navigationKey`
  is the payload — one string, the destination. Named for the web
  Navigation API's traversal (`navigation.traverseTo(key)`); it is only
  ever backwards, to a route beneath the top of the shown chain. ABI kind
  29 on Apple and the wasm web host; `traverseTo` in the JS target.
- **`backTo(r, key)`**: pop the selected stack to the entry whose id, as
  a navigation key writes it (`${e.id}`, the 1038 D6 idiom), is `key`.
  The top's key is unchanged; a key not in the selected stack is
  refused, unchanged, with one journal line. `back_to(r, id_of(stack[i]))`
  equals `back` applied until that entry is the top (a corpus law over
  every recorded value, `route/tests/corpus.rs`).

```
main navigationKey=`${top(nav).id}` navigationBack="back" traverse=returnTo
action returnTo(entry: string)
  nav = backTo(nav, entry)
```

**How the two paths relate** — one rule, by what the root declares:

- The root declares `traverse`: every platform Back of any depth — UIKit's
  back button, its menu, the swipe, a sheet pulled down with what it
  pushed, nested sheets, the browser's Back over one entry or several —
  is one `traverse(K)`. No Back control is pressed. Work a screen does as
  it is left belongs in that one action (Lexy resets its login preview
  when the top it leaves is `login`).
- It does not: each screen left presses *its own* `navigationBack`
  control, resolved anew in the then-active route, once per screen, with
  projection suspended until the last (no intermediate stack is pushed:
  B1's bounce). A press that leaves the chain unchanged is a refusal and
  stops the loop. On the web a multi-entry Back without `traverse` stays
  `navigate(url)` (1038 D7).

Either way delivery happens before anything is projected; if `K` has left
the app's chain since (it went elsewhere) nothing is delivered and its
state wins; and if the app refuses, the projection that follows puts the
screens back — visible and deterministic (1035.001 D2's "revocation
re-presents", generalized). A sheet's backdrop (`closedby="any"`) asks for
the same change, back to the route beneath the sheet. `select(T)` presses
the tab's `navigationTabControl`.

### D5 — App → native: project the latest tree when nothing is in flight

`sync` projects only when nothing is in flight, nothing is owed and no
settle is pending; otherwise it marks dirty, and the settle that ends the
wait projects the latest tree. Installing the tab bar controller and
switching tabs wait too (B3: the old stack's completion is no longer
lost). After projecting, `applied` is what UIKit reports (it updates
`viewControllers` synchronously, animated or not); a call UIKit did not
take is journaled and never mistaken for the person's. A presentation
that cannot start because the owner already presents (an alert, a
popover, the share sheet, anything a module put there) leaves dirty set
and is retried: the menus, popovers and the share sheet settle as they
leave, and a 0.3 s retry catches the rest (B6). Animation is unchanged
(1038 D6).

### D6 — Leaving is the app's to permit, projected where UIKit offers a switch

A route's own Back control decides: enabled, leaving is permitted;
disabled, it is not. A route with no Back control may be left when the
root hears `traverse` (the app is told by that event) and may not
otherwise (nothing could tell it). `NavigationRules.backPermitted` is the
one rule, projected three ways: the swipe recognizers' `shouldBegin`, a
sheet's `isModalInPresentation` (now for a sheet that has pushed a
screen too), and `navigationItem.hidesBackButton` on every route, which
hides the back button and its menu where leaving is refused (B4). A
platform path nobody can switch off still ends in D3/D4: the app is
asked, refuses, and the screen comes back. With `traverse`, the hidden
1×1 Back buttons apps wrote only so the platform had something to press
are no longer needed (Lexy keeps its for the agent driver and Escape).

### D7 — Controls are not state changes

UIKit chrome that acts as a button changes nothing native and presses the
app's control: tab bar items (`shouldSelect` → false), trailing bar
buttons. The app's answer arrives as an ordinary batch through D5.

### D8 — Containers

- **Stack:** pops of any depth by any mechanism: D3's prefix rule.
- **Sheet (`modal`)**, with any detents: its dismissal is the loss of its
  layer, back to the route beneath its boundary, however deep its own
  stack — so a sheet that has pushed a screen can now be pulled down, as
  every UIKit sheet can. Detents are not state.
- **Full screen (`fullscreen`)**, the iOS 18 zoom included: the same
  (by construction — its dismissal ends in the same delegate and
  completions — but no fixture exercises it yet).
- **Nested presentations:** one change for however many layers left.
- **Alerts, action sheets, popovers, menus, share:** not navigation; an
  alert over a sheet holds the sheet (UIKit refuses its pull-down), and
  a sheet asked for while one is up or leaving starts after (D5).
- **Tabs:** selected by the app (D7) — except through the **More list**,
  which UIKit owns entirely and which is supported as UIKit does it, with
  no count of five written anywhere: More opens (`shouldSelect` lets it);
  a tab chosen in it is observed as `select(T)` and told to the app; a
  stack tab shown there has its screens handed by UIKit to the More
  list's navigation controller, which the routes then drive (pushes and
  pops inside More, back to the list); the list open at its root is
  chrome and changes nothing. **More's Edit** rearranges the bar: the
  routes say which tabs exist, and the order they show in is the
  person's, kept as UIKit keeps it — presentation, as a detent is —
  reported in `state.navigation.tabs`, never rewritten by a projection.
- **Containers the app's module supplies** (`navigationContainer`, Q3 of
  r1): projection only. The host gives the module the tab's screens, as
  the routes name them; navigation inside the module's own UI is the
  module's, not a route, and is not observed. Simple for the developer —
  the module is a view of the routes, not a second router; correct for
  the app — its routes change only by its actions; and for the OS — the
  module's own controller behaves as UIKit expects. A module that wants
  its UI to move between routes presses the app's controls, as any other
  native view does.

### D9 — `state.navigation` reports the record

Beside `route`, `stack` and `transition` (whose phase is now
`in-progress` or `idle`): `native` (observed), `applied`, `app` (the
tree's snapshot), `owed`, `reported` (the last change told to the app),
and `tabs` (the order UIKit shows). `completed`/`cancelled` are gone: they
described a gesture, not a state.

## 3. What this removed

`interactiveSource`, `interactiveDepth`, `interactiveTransition`,
`lastTransition`, `changing`, `pendingSync`, `replacedBack`,
`NavigationRules.dispatchesBack`, `NavigationRules.poppedByPlatform`,
`invokeBack`/`canInvokeBack`, the sheet delegate's own Back press, and
the "sheet's root must be the selected key" refusal. `popMayBegin` keeps
its permission half; its `changing` argument is now `inFlight`.

## 4. Verification

1. **Pure** (`NavigationRulesTests`, macOS): `platformChange` over the back
   button, the menu, a cancelled swipe, a non-prefix, a sheet with its
   pushed screen, a pop inside a sheet, nested sheets, a More selection;
   destinations surviving the app moving meanwhile (`backs`); the
   permission rule; `popMayBegin` and the viewport freeze with `inFlight`.
   **Router:** `back_to` is `back` until the entry is the top, over every
   reachable value in the corpus; a key not in the stack is refused
   unchanged. **Contract:** `traverse` delivers a key and `backTo` pops to
   it; a stale key is refused and journaled; `traverse` refuses captured
   arguments, a non-string payload and any node but the navigation root.
2. **Simulator, real chrome** — `apps/nav-fixture` (seven tabs, three deep,
   a sheet that pushes, an alert over a sheet that asks for a second
   sheet as it leaves) and `apps/nav-fixture/sim.mjs`, which drives it
   with `axe` on a normally launched app and waits, by polling the
   accessibility tree, for both what UIKit shows (the bar's title) and
   what the app holds (each screen prints its route and how many
   `traverse`s and Backs it heard), then checks that it holds for a
   second (no bounce). Steps: the back menu three deep (one `traverse`),
   the back button, the edge swipe, a cancelled swipe (nothing), a sheet
   pulled down with its pushed screen (one `traverse`), an alert over a
   sheet (the pull-down refused), the sheet the alert's answer asks for
   while it leaves (B6), each of two nested sheets pulled down, More: a
   tab chosen in the list, a push and pop inside it, back to the list,
   another tab; More's Edit putting a tab on the bar, which keeps it.
   All pass. The fallback (no `traverse`: Back per screen) was driven the
   same way on a Lexy variant: the back menu three deep, the back button,
   the swipe, a cancelled swipe, a sheet with a pushed screen.
3. **Lexy**, launched normally, with `traverse=returnTo`: tabs, the back
   button, the swipe, Last Parked pulled down and reopened.
4. **Web:** on the JS target, the fixture's `history.go(-3)` from three
   deep is one `traverse` and lands at `/`; `history.back()` is one
   `traverse`; Lexy's `history.go(-2)` lands on Settings.

The old host, driven the same way, showed B1 (r1, §1). A UIKit XCTest of
`NavigationHost` itself needs a live session (it projects only in a
window), so the reconciler's UIKit half is held by the simulator run.

## 5. What this amends, at acceptance

- LLP 1035.001 D1: "the Back control must exist and be enabled for an
  interactive pop or sheet dismissal to begin" becomes D6's rule (a root
  that hears `traverse` needs no control to be left). D2: "completion
  presses Back once" becomes D3/D4; the interactive-source repair and its
  exception are subsumed.
- LLP 1038 §3: a seventh verb, `backTo`; D4's "six verbs" becomes seven;
  D7: a Back over entries still beneath the selected route is one
  `traverse` where the root declares it; D8: `traverse` beside `navigate`.
- LLP 1035.002 D2: `state.navigation` gains D9's fields.
