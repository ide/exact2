## Summary

Exact's native chrome talks to the app through **proxy controls**: the
navigation root's `navigationBack`, a tab route's `navigationTabControl` and
a route's `navigationTrailing` each name, by HTML `id`, a button the app must
author, and the host "presses" it. Apps author invisible 1×1 `opacity=0`
buttons only so there is something to press — Lexy has eight. Each is a
second identity for something the platform owns, sits in the accessibility
and focus order, has a position (Lexy's scenario chooser first opened from a
point under the status bar), and needs a synthetic activation path. That
synthetic path is where `1b25edc8`'s bug lived: the bar button looked for a
`press` handler, Lexy's control had only `popovertarget`, and nothing
happened.

A second, independent defect: **activation is not one thing.** On iOS about
twenty call sites decide what activating a control means, and only touch
and native buttons learned that an invoker (`popovertarget`, `commandfor`)
opens its target: Enter/Space and VoiceOver cannot open a confirmation
whose invoker has no `press`. macOS has one entry point but resolves the
command *before* the action runs.

This RFC removes each proxy by naming what it *meant* and giving that its
own declaration, and makes activation one algorithm on both Apple hosts:

| The proxy meant | Now |
|---|---|
| `navigationBack` present: "this element is a navigator" | structural: `navigationKey` with keyed children (D2) |
| `navigationBack` disabled: "leaving is refused" | `closedby="none"` on the route — HTML's close-request vocabulary, extended to routes (D3) |
| `navigationBack` pressed: "the platform went back" | `traverse(K)` only; the press-until-destination fallback goes (D4) |
| `navigationTabControl` pressed: "the person chose tab T" | `tabselect(T)` on the navigator (D5) |
| `navigationTrailing(+Symbol)`: "a bar button" | real buttons in the route's `role="toolbar" toolbarPlacement="navigation-bar"` (D6) |

## 2. Decisions

### D1 — Activation is HTML's, once per host

`Presenter.press(id)` is the one activation on iOS and macOS. Touch, keys,
VoiceOver, native and bar buttons, menu rows, segments, swipe actions and
the agent all call it; the raw dispatch (`onPress`) is reachable from
nowhere else. For a node that is a view:

1. **Eligible** — live; not `disabled` (itself or a container); not
   `inert` (a modal `dialog` escapes the inertness above it, as
   `showModal` does); not in a route the navigator has not selected. Else
   nothing, journaled.
2. **The action** — the node's `press`, when it has one. The runner
   applies it synchronously.
3. **Eligible again** — HTML's button activation runs its command only if
   the button is still not disabled: an action that disables, removes or
   moves its own invoker out of the selected route ends activation here.
4. **The command**, read now from the node's *current* attributes toward
   its *current* target — never captured before step 2:
   - `popovertarget` + `popovertargetaction` (`toggle` default, `show`,
     `hide`) toward a `popover`;
   - `commandfor` + `command`: `show-popover`/`hide-popover`/`toggle-popover`
     toward a `popover`; `show-modal`, `close`, `request-close` toward a
     `dialog`. `commandfor` wins when both are present; a command not
     applicable to its target does nothing.
   - `close` closes. `request-close` is a close request: the dialog's
     `cancel` handler (when it has one) hears it, then it closes — explicit,
     so `closedby` does not gate it.

   The target's kind picks the platform adapter: a confirmation
   (`dialog`/`alertdialog`) is UIKit's alert or action sheet (or AppKit's
   dialog layer); a content popover UIKit's popover. Shapes an adapter does
   not support stay refused and journaled, as today (a native confirmation
   still needs `closedby="any"`): bounded, never promised.

Ids that are not views (an SVG element, an inline run) have step 2 only.

**Target resolution** is part of activation: one predicate,
`activatable` (has `press`, or commands a confirmation or content popover),
decides what a touch lands on, what Enter/Space activates, what VoiceOver's
activation reaches, what the hardware Tab ring includes, and what the agent
may tap.

**D1a — Menus.** A popover of button rows is a native menu (LLP 1021),
which only its UIKit button can open: the transparent overlay over an
authored invoker, or a projected bar item's own `menu` (D6). Its
`UIDeferredMenuElement` provider is the activation: it calls
`press(invoker)` (steps 1–3), then resolves the invoker's current target
and reads that popover's rows, and always calls its completion — empty when
the invoker is gone or refused. A `press` of a menu invoker from elsewhere
(the agent, a key on the authored node behind the overlay) runs steps 1–3
and journals that a menu opens from its button. Agent drives keep seeing a
menu's rows inline (LLP 1021 D4).

**D1b — Anchors.** A presentation points at what the person activated:
the bar item a projected node is shown as (`sourceItem`, D6), else the
node's own box. `Presenter.anchor(for:)` is that lookup; the `anchor:`
parameter of `1b25edc8` goes.

macOS's `PresenterMac.press` and `DialogsMac.command` adopt steps 1–4 (the
command read after the action), so both hosts implement one definition.

### D2 — A navigator is structural

> An element with a `navigationKey` that has at least one child with a
> `navigationKey` is a **navigator**; those children are its **routes**,
> the one whose key is the navigator's is selected.

Children are the authored, logical tree (the kernel's), never UIKit's or
AppKit's view containment, which moves routes under controllers. A keyed
element with no keyed children is a route, or nothing; a navigator whose
routes are momentarily all absent is dormant (nothing projected, nothing
refused). The **first** navigator — the outermost, in tree order — is the
document's: it alone takes `navigate` (URLs: 1038 D8) and is projected
natively on iOS. Any navigator takes `traverse` and `tabselect`.
`lower-navigate-root` keeps `navigate` on a keyed first root and checks
`traverse`/`tabselect` sit on a keyed element. Every host, the runner's
head selection and both web targets use this one predicate; the CSS form
is `[navigationKey]:has(> [navigationKey])`.

### D3 — Leaving is refused by `closedby`, on any route

HTML's `closedby` says which requests close a dialog: `any` (light dismiss,
close requests, the app), `closerequest` (close requests and the app),
`none` (the app only). A platform Back — the bar's back button and its
menu, the swipes, a sheet pulled down, VoiceOver's escape, Escape, the
browser's Back onto an entry the app still holds — is a close request on
each route it removes. Exact extends the attribute to every route (an
Exact extension, declared as such in the kernel spec; HTML's own default
for a dialog depends on modality, Exact's for a route is `closerequest`;
`any` additionally lets a sheet's backdrop close it):

> A platform Back to K is permitted when the navigator hears `traverse`
> and **no route it removes** — every route above K in the selected chain —
> has `closedby="none"`.

`NavigationRules.backPermitted(removed:traverses:)` is that rule, applied
where each platform asks before acting: the swipes' `shouldBegin` (removing
the top), a sheet's `isModalInPresentation` (removing its boundary and
everything pushed in it — both owners, as today), `hidesBackButton` (the
top), the web's header back, backdrop and drag (their destinations), and
Escape. A path no one can stop beforehand (the back button's menu choosing
deeper than a refusing route, the browser's Back) is checked at delivery:
a refused Back is not delivered — the projection restores the screens on
iOS, and the history mirror restores the entry on the web. The app's own
controls work under any value.

### D4 — Back reaches the app only as `traverse`

The fallback is deleted on every host. Each platform Back is one
`traverse(K)` (I1):

- **iOS** — observed, unchanged (1035.001.000 D3). Escape on a hardware
  keyboard and VoiceOver's escape are UIKit's own pops, observed.
- **Web chrome** — the header back button delivers `traverse` to the route
  beneath the top in its presentation (the stack's previous route), never
  `history.back()`: the previous history entry may be another tab's or
  none (a deep link boots a stack whose lower routes have no entries). The
  mirror then reconciles history with the commit, as for any app change.
  A sheet's backdrop (`closedby="any"`), its drag-down and Escape on a
  sheet deliver `traverse` to the route beneath its **presentation
  boundary** (the last route below the topmost `modal`/`fullscreen` route),
  so a sheet that pushed a screen leaves whole; Escape on a pushed screen
  goes back one.
- **Browser Back/Forward** keep 1038 D7: an owned entry still beneath the
  selected route is `traverse` (after D3's check); anything else — a tab
  switch undone, Forward, an entry the app removed, a bfcache restore — is
  URL navigation through `navigate`, with the mirror's refusal and
  redirect reconciliation as today.
- **macOS/Linux Escape** — `traverse` to the same destination as the web's.

A navigator without `traverse` gets no platform Back: no native back button
or swipe; a refused header/backdrop; the browser's Back goes through
`navigate` or is refused and restored.

### D5 — Choosing a tab is `tabselect`, carrying the tab's name

`tabselect` on a navigator: the person **asked for** tab T (its routes'
`navigationTab`) — every choice, the tab already shown included. What the
app does with it is the app's: `select` restores T's retained stack and,
for the tab already shown, pops it to its root (the router's policy, as
UIKit's reselect).

```
main navigationKey=`${top(nav).id}` navigate=followLink traverse=returnTo tabselect=selectTab
action selectTab(name: string)
  nav = select(nav, name)
```

One helper per host delivers it, from:

- iOS `shouldSelect` on a bar item (it returns false; the app's batch
  selects, through 1035.001.000 D5);
- iOS **More**: the choice itself, observed where UIKit reports it — the
  More list's navigation controller showing a tab's container
  (`willShow`) — delivered once, including the tab already shown, and
  never inferred from a snapshot diff. Opening the list is presentation;
  More's Edit order stays UIKit's;
- the web tab bar's buttons.

Without `tabselect` a tab bar is still drawn; a choice is refused and
journaled. The web tab bar is a `nav` landmark of buttons with
`aria-current="page"` on the shown tab — app navigation, not ARIA tabs
(which are panels within one view and need roving focus): each button is a
tab stop, Enter/Space choose it, focus never selects.

### D6 — A route's bar buttons are real buttons in its toolbar

```
column navigationKey=`${e.id}` navigationTitle="Login Flow" …
  row role="toolbar" toolbarPlacement="navigation-bar"
    button aria-label="Preview Scenario" popovertarget="scenario-chooser"
      image symbolName="wrench.and.screwdriver"
  …
  column id="scenario-chooser" popover …
```

This extends the shape macOS projects into the window
(`role="toolbar" toolbarPlacement="window"`, `ToolbarMac.swift`): an ARIA
toolbar, authored where it belongs, which the host shows in the platform's
bar where it has one, its nodes and actions surviving.
`toolbarPlacement="navigation-bar"` names the route's navigation bar
(SwiftUI's `ToolbarPlacement` vocabulary, as `window` is). Within it a
button with `toolbarPlacement="navigation"` is leading (macOS's meaning of
the item value); the rest trail, in authored order.

**Ownership.** A route's toolbar is its first direct child with that
placement; a second is refused and journaled. Its bounded shape is direct
buttons (macOS's, without the heading: the bar's title is
`navigationTitle`). It is projected only where the route shows a native
bar (it declares `navigationTitle`); otherwise, or when its shape is not
supported, it keeps its authored rendering. The authored element is hidden
(and hidden from accessibility) only after the items are installed.

- **iOS:** `navigationItem.leftBarButtonItems` (with
  `leftItemsSupplementBackButton`) and `rightBarButtonItems`. Each item
  mirrors, every projection: its image (a native button's face symbol, else
  a child `image`'s `symbolName`, else its text as title),
  `accessibilityLabel` (`aria-label`, else text), `accessibilityIdentifier`
  (`testId`), `isEnabled` (not `disabled`/`inert`). Its action is
  `press(node.id)` (D1); an invoker of a menu gets the item's `menu` with
  D1a's provider. The node → item map is `anchor(for:)` (D1b). Keyboard
  focus on bar items is UIKit's own (Full Keyboard Access), as in every
  native app; Exact's Tab ring covers content and skips the hidden authored
  toolbar. VoiceOver reaches the items natively.
- **Web:** the authored toolbar is a real element in the route; the
  chrome's CSS lays it in the bar row, its `navigation` buttons in the
  leading area after the back button, the rest trailing. Toolbar keyboard
  behaviour is the APG's: one tab stop, arrow keys move within (the chrome
  adds this for projected toolbars).
- **macOS/Linux:** no per-route bar; the authored toolbar renders where it
  is.

### D7 — The agent drives the chrome as root-scoped taps

The nine operations stay nine (LLP 1012):

- A projected toolbar button is an ordinary node: `tap` runs `press` (D1),
  anchored to its item.
- `tap <navigator> back`: the platform's Back from the navigator's top, as
  its back button would — refused when no back button is shown (D3), when
  a presentation (alert, menu, popover, share sheet) covers it, or while a
  transition is in flight. iOS: UIKit's pop of the shown stack, observed
  and delivered as any other; web: the header back's `traverse`.
- `tap <navigator> tab <name>`: the tab bar's choice of `name` — through
  More when UIKit shows it there — delivered by D5's helper; refused for a
  tab the navigator does not have or under a covering presentation.
- `type <navigator> key Escape`: the close request, through the same
  arbitration as a hardware Escape (the topmost presentation first).
- `tree`/`state` report what the chrome offers (`state.navigation`:
  whether Back is shown, the tabs in UIKit's order).
- `type <navigator> <location>` delivers a location (1038 D11), unchanged.

### D8 — Deleted, with every consumer migrated in the same change

`navigationBack`, `navigationTabControl`, `navigationTrailing`,
`navigationTrailingSymbol` leave the schema and the attribute table; using
one is `lower-unknown-attr` with a hint naming its replacement. Deleted:
the fallback, `backPermitted`'s control arguments,
`NavigationRules.backControl`, `NavigationIOS.activate`/`pressControl`,
`MenuHost.invokeConfirmation`, the web's `pressBack`/`pressBackTo`/`standsIn`
and the `anchor:` parameter. No shims (RULES).

## 3. Migration

- **Router-backed apps and plans** (`nav-fixture`, `messages`,
  `messages-legacy`, `realworld`, the corpora's router plans, the
  conformance router/heads plans): drop `navigationBack`; declare
  `traverse=returnTo` (`nav = backTo(nav, entry)`), and `tabselect` where
  tabbed; delete controls whose only purpose was proxy delivery; keep real,
  visible Back buttons (Messages') and their effects; bar buttons become
  route toolbars.
- **Manually keyed fixtures** (`navroot.contract`, the Linux and wasm tests
  with `navigationKey=selected`): drop `navigationBack`; where a test needs
  platform Back, a string handler of its own sets its local state.
- **Lexy:** all eight proxies go — 4× Back (`traverse`, plus `closedby`
  where a Back control was disabled), 3× tabs (`tabselect=selectTab`, which
  keeps its `mapsRev` bump), the scenario wrench and the map's close (route
  toolbars).
- **Docs:** `contract-for-humans.md`, `contract-grammar.md`,
  `contract-for-agents.md`.

## 7. As built (r3)

- **The backdrop is a close request**, as UIKit's dimming view is (UIKit
  dismisses a sheet on a tap there unless `isModalInPresentation`): the web
  backdrop delivers `traverse` beneath the sheet unless D3 refuses, not
  only under `closedby="any"`.
- **Escape closes the topmost presentation** (a sheet or cover, with what
  it pushed) — the web's keydown, and the agent's `type <navigator> key
  Escape` on iOS. It does not pop a pushed screen: no platform maps Escape
  to a stack Back. Hardware Escape and VoiceOver's escape on iOS stay
  UIKit's own, observed.
- **A route toolbar keeps its layout box** while hidden on iOS (the kernel
  lays it out where it is authored), so it is authored out of flow
  (`position="absolute"`); on the web the chrome's CSS takes it out of flow.
  Its items are reassigned only as they change: a reassigned bar item
  rebuilds its button and drops a touch already down on it.
- **A projected button is visible to activation**: the menu adapters treat a
  button shown as a bar item as shown, though its authored view is hidden.
- **macOS and Linux** draw no navigation chrome: they take the navigator
  predicate, the `traverse`/`tabselect` hooks, and (macOS) D1's order —
  the command read after the action. Escape as `traverse`, and the agent's
  chrome taps, are not wired there (QUEUE).
- **`request-close`** closes as `close` does on iOS; its `cancel` event to
  the dialog is not delivered yet (QUEUE).
- **A dialog the state holds open** (`open`) closes when its state does: a
  `close` command toward it is the app's to answer, so the alert stays until
  the state changes (QUEUE).
- **iOS projects the first root only**: a navigator wrapped in a plain
  element is not taken into UIKit's containers (as before this RFC); the web
  projects any navigator (QUEUE).
